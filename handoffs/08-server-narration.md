# Handoff 08 — Server narration through Shadow Controller

## Client request and queue

The client exposes two narrative entrypoints through its MCP server: `shadow_submit_narration` for a chat brief and `shadow_submit_narration_file` for an explicitly selected UTF-8 file. The file tool reads and sends the file itself, so the client model does not need to inspect it before submission. Both send `narrative.generate` v1 with `projectId`, `projectSha256`, `brief`, optional `metadata`, and a stable request ID. Requests are authenticated, size-checked, persisted in the server SQLite FIFO queue and idempotent by request ID. Duplicate submissions return the existing job; conflicting reuse is rejected.

If the Coordinator restarts while a job is active, it records the interrupted attempt, checks tracked child-process markers, and waits if a child is still alive or cleanup is unverified. Once safe, it unloads any job-owned Writer left by the interrupted attempt, moves the previous run directory to `runs/recovered/` without deleting its logs or partial artifacts, and automatically queues a fresh attempt for the same job. Attempt history is retained in SQLite. Since a crash can occur after a model call or upload, recovery may repeat model work; the Coordinator publishes a new canonical OneDrive scene only after the new result passes hash verification.

`projectSha256` is currently an identifier supplied by the client. The server does not resolve a project registry or retrieve canonical project contents from that hash. If the client has authorized canon text, it can be included in `metadata.canon`; otherwise the Writer receives only the brief and the result records that the canon was absent. Do not claim that the server verified the revision or that the brief's content is approved merely because the hash is present.

## Server workflow

The server Coordinator executes one job at a time and uses the original brief and available canon directly. It does not ask Codex to plan or draft a proposal before Writer generation.

1. The Writer creates the entire server artifact in English, including dialogue, even when the request or dialogue examples are in another language. It translates their meaning and voice while preserving proper names and canon. The `## Scene Setup` section describes the opening tableau before `## Narrative`, which always starts with a standalone `> Visual:` cue. Dialogue and short action beats follow, and `## English Summary` closes the artifact. Cues are directions in text; the narration operation does not generate images, audio or animation assets.
2. The Coordinator validates the draft without a model call. It checks the heading sequence, nonempty sections, the opening Visual cue, dialogue line structure, and a lightweight foreign-language heuristic for the scene body. The heuristic is a revision trigger, not a complete language classifier. It does not validate dialogue-to-narration balance or sound density. Hemmingway receives those craft requirements in its system prompt; the final editor receives them in the shared Codex/Venice editing prompt and must make the corrections directly. In ordinary dialogue-led scenes, spoken words should exceed narrative/action prose, excluding Visual cues. Adult intimacy/sex, fights, action, suspense, physical tasks, and deliberate quiet are exceptions when characters naturally speak less. Long narrator passages may be redistributed among concise Narrator voiceover, a supported Visual direction, and/or a brief summary with a written sound; every form is optional and combinable, without duplicating facts. Adult erotic scenes and sparse-dialogue action/fight scenes should contain several varied written sound forms, including vocalizations and non-vocal sounds when supported; breath description alone does not satisfy this. Sounds are prose/dialogue, not optional NCF production cues. The exact Writer system prompt is saved as `writer-system-prompt.md` with the run evidence.
3. The Coordinator returns every detected issue to the Writer for a focused revision, up to five revisions. It records the issues per draft. A scene that still fails the checks after final editing is kept in the run directory and is not published.
4. Codex receives the original brief, available canon, latest usable draft and draft validation outcomes. The shared editing prompt tells the final editor to apply dialogue-balance exceptions, break up excessive narrator passages into optional composable voiceover/visual/sound forms, improve dialogue and punctuation, and add contextual written sounds where sparse-dialogue intimacy or action needs them. It must make the prose less mechanical and make diction, fluency, rhythm, reactions, and sounds fit each character and the immediate situation, without turning background or intoxication into caricature. Codex and Venice receive the same editing prompt and must make these corrections directly. Accept only a scene matching the required artifact envelope. On a Codex refusal, process failure, timeout, or invalid artifact, record the reason and send the same editing prompt to Venice once. Accept the Venice edit only if it matches the envelope. If Venice fails, preserve the latest usable draft and record the fallback error.
5. Validate the selected scene, save stage evidence and the local manifest, upload it with rclone to `imagecloud:NarrationWorker/final/<jobId>/scene.md`, and download/read back the remote bytes. Compare SHA-256 before returning a reference.
6. Unload the job-owned Writer model after the complete review cycle. Codex must exit before delivery. Cleanup failure is included in the manifest and changes an otherwise usable result to `completed_with_warnings`. Cancellation and ordinary failures preserve evidence. A Coordinator restart triggers safe automatic recovery of an interrupted active job as described above.

The narration worker selects Hemmingway directly. Optional environment settings are `SHADOW_LM_API_BASE_URL` (default `http://127.0.0.1:1234`), `SHADOW_NARRATION_CONTEXT`, `SHADOW_LMS_EXECUTABLE`, `SHADOW_GEMINI_EXECUTABLE`, `SHADOW_CODEX_EXECUTABLE`, and `SHADOW_RCLONE_EXECUTABLE`. The default review backend is `deterministic-codex`. Set `SHADOW_NARRATION_REVIEW_BACKEND=writer-only` to use deterministic checks and Writer revisions without a final model editor. The legacy `gemini-codex` setting selects the same deterministic path. Venice authenticates using `VENICE_API_KEY` or the existing Venice CLI configuration for the server account. Its default model is `deepseek-v4-1-flash-uncensored` and can be changed with `SHADOW_VENICE_MODEL`. Before sending any story content, the worker checks whether the key has API access on a non-charged tier and whether the model is listed in the key rate limits. Otherwise it records `venice_free_access_unavailable` and keeps the latest usable draft. The Coordinator does not copy the key to job files. An experimental local path is enabled with `SHADOW_NARRATION_REVIEW_BACKEND=qwen`, which defaults to LM Studio model `qwen2.5-14b-instruct-abliterated-v2`; the default Qwen mode is `direct-edit`. Set `SHADOW_NARRATION_REVIEW_MODE=feedback-loop` to use up to five Qwen review/Writer-revision cycles followed by a Qwen final edit. This path unloads the active model before loading the other and verifies cleanup before delivery. The same server account needs the configured LM Studio models, `lms`, Codex CLI when using the default backend, and the rclone `imagecloud:` remote.

The 6 November 2026 local normal-scene comparison did not promote Qwen. In feedback-loop mode it returned `PASS` without feedback despite an explicit event-order violation, and its final output was byte-identical to the draft. In direct-edit mode Qwen returned the draft unchanged in two runs and left cue directives that the brief disallowed. The comparison predates the switch from Gemini to deterministic draft checks on the server. Test evidence is in `production-tests/shadow-narration/20261106_qwen-reviewer-mode-comparison/report.md`; these direct-worker runs bypassed Cloudflare, relay authentication, MCP submission and the SQLite queue.

## Result and client retrieval

The authenticated job status includes the server result manifest. It carries `jobId`, `requestId`, manifest status (`succeeded`, `completed_with_warnings`, `failed`, or `cancelled`), `narrativeRemotePath`, `narrativeSha256`, `projectSha256`, `selectedDraft`, `writer` (the Writer model ID for the delivered scene), `reviewer` (`codex`, `venice`, or `none` for the selected final edit), stage outcomes/attempts/error codes/reasons, and warnings where applicable. A path and hash are returned only for a usable, remotely verified scene. Draft validation findings are recorded in the stages and are not counted as a final edit. Queue state may be `succeeded` while the manifest status is `completed_with_warnings`; the manifest is authoritative for stage outcomes.

The client calls `get_narration_result` with `jobId`. That MCP tool resolves the authenticated job status, downloads only the expected OneDrive path through rclone, verifies the SHA-256, and writes an exclusive local copy. The client must complete this download and integrity check before reading or analysing the scene. A failed verification returns an error and no usable local path.

The client skill is [Shadow Requests](../apps/shadow-client/skills/shadow-requests/SKILL.md), included in the client package and installed with `shadow-client install-skill`. The standalone local planning role is separately documented in [Handoff 09 — Bionic Regia](09-bionic-regia.md).
